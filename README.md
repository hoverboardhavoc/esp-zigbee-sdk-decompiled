# esp-zigbee-sdk-decompiled

Per-function decompiled history of the binary blob(s) matching
`components/esp-zigbee-lib/lib/esp32c3/*.a` from
[espressif/esp-zigbee-sdk](https://github.com/espressif/esp-zigbee-sdk), mechanically
generated by Ghidra and committed in step with upstream changes.

## What's in the repo

- `decompiled/<archive>/<member>/<function>.c` — one file per function
  inside each `.o` member of each matched archive. The file's body is the
  Ghidra decompiler's C-like output for that function. The header lines (a
  leading `/* ... */` block) identify the upstream commit that last actually
  changed that function's decompiled body.
- `processed/<sha>.done` — sentinel files recording which upstream commits
  have already been processed by the pipeline.
- `LICENSE`, `NOTICE` — Apache License 2.0 text and derivative-work attribution.

## Why

Espressif ships this support as a closed binary blob with no source
code. This repository tracks the blob's evolution at the function level:

- `git log decompiled/<archive>/<member>/<function>.c` shows when each
  function's decompiled body changed and which upstream commit caused the
  change.
- `git diff <commit_a>..<commit_b> -- decompiled/` shows only the functions
  whose decompiled output differs between two upstream releases, not every file
  in the tree (per-function headers are written only when the body changes, so
  the diff is the real change set).

## How it works

- `scripts/process.py` (Python 3, standard library only) drives the pipeline:
  1. Clones / fetches the upstream repo (espressif/esp-zigbee-sdk).
  2. For each commit touching a blob matching `components/esp-zigbee-lib/lib/esp32c3/*.a` (oldest first)
     that lacks a `processed/<sha>.done` sentinel:
     - Checks out the upstream commit and copies the blob(s).
     - Detects each blob's processor (RISC-V architectures are decompiled;
       architectures with no bundled Ghidra processor are skipped and logged).
     - Extracts `.o` members with `ar x`.
     - Runs Ghidra headless on each `.o`, invoking `scripts/DecompileDump.py`
       as a postScript to emit one `.c` per function into a scratch directory.
     - Compares each decompiled body against the existing file (stripping the
       header). If the body is identical, the existing file is left alone, so
       its header continues to point at the earlier upstream commit where it
       last changed. If the body is new or different, the file is rewritten
       with a header naming the current upstream commit.
     - Removes files for functions no longer present.
     - Marks the commit processed and makes one git commit per upstream commit,
       authored on the upstream commit's date and committed by `blobmaster`.
- Each run processes at most `MAX_COMMITS_PER_RUN` upstream commits (set in
  `.github/workflows/process.yml`, default 25) so a single sweep stays inside
  the runner time limit. When more commits are unprocessed than that cap, the
  run stops early with commits still pending and reports how many remain.

## Keeping the repo current (manual drain)

Updates are primarily a **manual drain**. The bundled
`.github/workflows/process.yml` carries a daily `schedule:` trigger
(`cron: '0 7 * * *'`), but on a fork that schedule is **best-effort only**:
GitHub heavily throttles scheduled workflows on forks (in practice a handful of
fires per day, hours apart) and disables them entirely after 60 days with no
repository activity. So the cron is a bonus catch-up, not a dependable
mechanism — manual `workflow_dispatch` remains the reliable way to keep the
repo current. No personal access token is required — the workflow commits with
the built-in `GITHUB_TOKEN`.

Because each dispatch drains only `MAX_COMMITS_PER_RUN` commits, catching up
after a backlog takes repeated dispatches:

1. Run the workflow — **Actions → process → Run workflow** on `decompiled`, or
   `gh workflow run process.yml --ref decompiled`.
2. When it finishes, check the run summary for the count of commits still
   remaining.
3. Re-run the workflow until a run reports **0 commits remaining** — at that
   point `decompiled` is caught up to the upstream blob history.

Alternatively, a machine with Ghidra can run `python3 scripts/process.py`
locally and push the `decompiled` branch.
